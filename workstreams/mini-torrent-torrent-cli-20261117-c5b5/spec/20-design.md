# mini-torrent — дизайн

Компактный CLI-клиент `mt`: одна команда добавляет закачку, фоновый демон её
тянет и переживает закрытие терминала и перезагрузку, TUI показывает, что
происходит. Личный инструмент на одну машину и одного пользователя.

## Устройство

### Один бинарь, три роли

`mt` — единственный исполняемый файл, который работает в одной из трёх ролей
в зависимости от подкоманды:

| Вызов | Роль | Что делает |
|---|---|---|
| `mt add <magnet \| файл.torrent>` | клиент | шлёт демону запрос на добавление, печатает имя закачки, выходит с кодом 0 |
| `mt` / `mt tui` | клиент | открывает TUI и держит подписку на снапшоты состояния |
| `mt daemon` | демон | торрент-движок, состояние, слежение за диском, сокет-сервер |

`mt daemon` — служебная подкоманда: пользователь её не вызывает, её запускает
сам `mt add`, launchd или systemd.

### Файлы проекта

```
main.go                       разбор argv, выбор роли
internal/config/config.go     чтение TOML-конфига, значения по умолчанию
internal/config/paths.go      пути конфига/состояния/сокета для macOS и Linux
internal/ipc/proto.go         структуры запросов и ответов (NDJSON)
internal/ipc/client.go        подключение к сокету, вызовы add/list/subscribe
internal/ipc/server.go        слушатель unix-сокета, роутинг запросов
internal/daemon/daemon.go     запуск роли демона: блокировка, сокет, движок, цикл
internal/daemon/engine.go     обёртка над anacrolix/torrent: add, прогресс, drop
internal/daemon/state.go      state.json: чтение, атомарная запись, снапшот
internal/daemon/watcher.go    fsnotify + периодический опрос файлов на диске
internal/daemon/spawn.go      самозапуск демона из клиента (detached)
internal/autostart/launchd.go установка LaunchAgent (macOS)
internal/autostart/systemd.go установка user-unit + linger (Linux)
internal/tui/model.go         состояние TUI, обработка снапшотов
internal/tui/view.go          отрисовка списка
```

### Данные и где лежат

| Что | Путь (Linux / macOS) | Формат |
|---|---|---|
| конфиг | `~/.config/mt/config.toml` | TOML, может отсутствовать |
| состояние | `~/.local/state/mt/state.json` | JSON, пишется атомарно |
| карта готовых кусков | `~/.local/state/mt/pieces.db` | BoltDB (piece completion движка) |
| копии метаданных | `~/.local/state/mt/meta/<infohash>.torrent` | бинарный metainfo |
| сокет | `~/.local/state/mt/mt.sock` | unix stream, режим 0600 |
| lock | `~/.local/state/mt/mt.lock` | flock, один демон на пользователя |
| лог демона | `~/.local/state/mt/mt.log` | текст, ротация по размеру |
| скачанное | `download_dir` из конфига, по умолчанию `~/Downloads` | файлы торрента |

Запись в `state.json`: `{infohash, name, source, download_dir, files[],
total_bytes, status, added_at, completed_at}`, где `status ∈
{downloading, done}`. Прогресс и скорость в состоянии не хранятся — они
живут в памяти демона и считаются на лету, после перезапуска восстанавливаются
из карты кусков.

### Потоки

- **Добавление:** `mt add` → сокет → демон читает конфиг, парсит magnet/файл,
  кладёт копию метаданных в `meta/`, заводит торрент в движке, дописывает
  запись в `state.json`, отвечает клиенту.
- **Прогресс:** движок качает все торренты параллельно; тикер раз в 500 мс
  собирает снапшот (байты, скорость за интервал) и рассылает его подписчикам.
- **Завершение:** торрент добрал 100% → `status=done`, торрент выбрасывается
  из движка, соединения с пирами закрываются.
- **Исчезновение файла:** watcher видит, что всех файлов торрента на диске
  нет → запись удаляется из `state.json`, торрент (если ещё активен)
  выбрасывается из движка, следующий снапшот уходит в TUI уже без неё.

## Решения

#### D-01: Go + библиотека anacrolix/torrent, один статический бинарь
Протокол BitTorrent не пишем сами — берём зрелую чистую Go-библиотеку
(DHT, трекеры, пиры, хранилище кусков) и собираем без cgo. Один файл `mt`
копируется на любую машину и запускается без рантайма и зависимостей.
**Функции:** FR-01, FR-02, FR-03, FR-05, FR-07, FR-09

#### D-02: Архитектура «тонкий клиент — демон» через unix-сокет
Вся работа идёт в демоне; `mt add` и TUI — короткоживущие клиенты, которые
только говорят с ним по `mt.sock`. Так закачка не привязана к терминалу,
а состояние существует в одном экземпляре. Сеть для IPC не нужна — всё
локально.
**Функции:** FR-01, FR-03, FR-05

#### D-03: Демон поднимается сам при первой команде
Клиент пробует подключиться к сокету; при отказе (нет файла или
`ECONNREFUSED`) запускает `mt daemon` отдельным процессом в новой сессии
(`setsid`, отвязанный от управляющего терминала, stdio в лог) и ждёт появления
сокета до 5 секунд. Ручного `mt start` не существует. `flock` на `mt.lock`
гарантирует, что гонка двух `mt add` не породит двух демонов.
**Функции:** FR-01, FR-03

#### D-04: Протокол — построчный JSON (NDJSON) поверх сокета
Три запроса: `add{source}`, `list{}`, `subscribe{}`. На `subscribe` демон
начинает слать по строке-снапшоту каждые 500 мс, пока клиент не отключится.
Ничего тяжелее (gRPC, HTTP) личному инструменту не нужно, а отладить можно
через `nc`.
**Функции:** FR-01, FR-05

#### D-05: Конфиг — необязательный TOML с одним обязательным смыслом
`~/.config/mt/config.toml` с ключом `download_dir` (и опционально
`listen_port`). Файла нет или ключа нет — берётся `~/Downloads`, каталог
создаётся при необходимости. Конфиг перечитывается на каждый `add`, поэтому
правка пути действует на новые закачки без перезапуска демона; уже идущие
докачиваются туда, куда начали.
**Функции:** FR-01, FR-08

#### D-06: Состояние и карта кусков — в каталоге состояния, отдельно от загрузок
`state.json` (список закачек, пишется через temp-файл + `rename`) плюс BoltDB
с отметками проверенных кусков и копии metainfo. Копия metainfo нужна, чтобы
возобновление не зависело от исходного `.torrent`-файла и от повторного
получения метаданных по magnet.
**Функции:** FR-04

#### D-07: Возобновление — автоматическое при каждом старте демона
Демон на старте читает `state.json`, поднимает все записи со статусом
`downloading` из сохранённого metainfo и отдаёт их движку с той же картой
кусков. Уже проверенные куски не перекачиваются, поэтому процент после
возобновления не ниже прежнего; команда пользователя не требуется.
**Функции:** FR-04

#### D-08: Автозапуск при загрузке ОС ставится сам, средствами платформы
При первом старте демон регистрирует себя: на macOS — LaunchAgent
`~/Library/LaunchAgents/dev.mt.daemon.plist` с `RunAtLoad`, на Linux —
user-unit `~/.config/systemd/user/mt.service` с `WantedBy=default.target`,
`systemctl --user enable` и `loginctl enable-linger` (чтобы демон жил без
входа в систему и переживал разрыв ssh). Это единственный способ выполнить
«после перезагрузки машины закачки возобновляются без команды пользователя».
Если регистрация не удалась, демон пишет предупреждение в лог и продолжает
работать.
**Функции:** FR-03, FR-04, FR-09

#### D-09: Никакой очереди — все закачки активны одновременно
Каждый добавленный торрент сразу отдаётся движку; лимита на число активных
торрентов нет, ограничение только на соединения на торрент. Три подряд
добавленных ссылки получают статус «качается» все три.
**Функции:** FR-02

#### D-10: Раздача выключена глобально, при 100% торрент выбрасывается
Движок настраивается с `Seed=false` и запретом исходящих блоков; по событию
завершения демон ставит `status=done`, вызывает `Drop()` — соединения с пирами
по этому торренту закрываются, анонс трекеру шлётся с `event=stopped`,
исходящий трафик становится нулевым.
**Функции:** FR-07

#### D-11: Слежение за диском — fsnotify плюс подстраховочный опрос
Watcher подписывается на каталог загрузок (inotify на Linux, kqueue/FSEvents
на macOS) и дополнительно раз в 5 секунд делает `stat` по файлам всех записей.
Если ни одного файла торрента на диске не осталось, запись удаляется из
`state.json` и из движка на живом демоне — перезапуск не нужен, следующий
снапшот уходит в TUI без неё.
**Функции:** FR-06

#### D-12: TUI — bubbletea, одна таблица, самообновление по подписке
`mt` без аргументов эквивалентна `mt tui`: клиент открывает `subscribe` и
перерисовывает таблицу на каждый снапшот (≈2 раза в секунду) без нажатий.
Колонки: имя, статус, процент, скорость; завершённые показаны в том же списке
со статусом «готово» и 100%. Клавиши только навигационные и `q` — TUI ничего
не меняет.
**Функции:** FR-02, FR-05

#### D-13: `add` принимает и magnet, и путь к файлу, различая их сам
Аргумент, начинающийся с `magnet:`, парсится как magnet-ссылка (имя подтянется
вместе с метаданными из DHT), иначе трактуется как путь к `.torrent` и читается
с диска. Одна подкоманда на оба случая, флагов не требуется; при успехе код
выхода 0, при ошибке — ненулевой и сообщение в stderr.
**Функции:** FR-01

#### D-14: Сеть — DHT, трекеры и PEX включены, порт случайный, проброс не нужен
Для скачивания достаточно исходящих соединений, поэтому UPnP/NAT-PMP не
делаем; порт слушаем на случайном свободном (или `listen_port` из конфига).
Источники пиров — трекеры из metainfo, DHT и обмен пирами. Интернет считаем
доступным; при его отсутствии демон просто не получает прогресса и продолжает
ретраить.
**Функции:** FR-01, FR-02, FR-04

#### D-15: Авторизации нет, граница доверия — права файловой системы
Пользователь один и локальный, поэтому в протоколе нет ни токенов, ни
проверок. Каталог состояния создаётся с режимом 0700, сокет — 0600, слушаем
только unix-сокет и никогда TCP, так что доступ имеет лишь владелец. Один
демон на пользователя обеспечивается `flock`.
**Функции:** FR-01, FR-03, FR-05

#### D-16: Пути и демонизация — через общий слой, без платформенных веток в логике
`internal/config/paths.go` отдаёт пути по XDG-переменным с запасным вариантом
`~/.config` и `~/.local/state` — одинаково на обеих системах, так что
пользователю не приходится помнить, где что лежит. Платформенно различаются
только два файла автозапуска (D-08). Команды `add` и TUI, их вывод и коды
возврата идентичны на macOS и Linux.
**Функции:** FR-09

## Открытые вопросы

- Пауза и удаление закачки из TUI: сейчас по договорённости TUI только
  смотрит, а запись уходит из списка при удалении файла с диска. Нужны ли
  эти действия — не решено, в дизайне их нет.
